# Same bunker, three existing workspaces

The hub's existing primary room actions remain unchanged. Its header exposes
Workshop, Facilities and Local Session. Each opens the already authored route,
not a new hub or replacement application. Back closes the workspace to the same
bunker and selected room; existing I/M/J navigation stays with CommonUI.

LocalBunkerWorkspaceBinding is a presentation binding selected only for a live
home campaign. It reuses authored panels and shared chrome, stops fixture
processing before first paint and reads immutable InventoryViews. Stock is
aggregated from unique (inventory,item) identities in authorized containers;
unavailable views remain unavailable rather than displaying false zero stock.
Refresh follows port/inventory signals, not frame polling.

Crafting presents the existing recipe-browser layout as a supply overview.
Recipe durations, ingredient requirements, output claims and sample queue are
not live systems and are removed. Craft/collect/upgrade stay disabled. The
existing loadout workspace remains the only way to manage those items.

Build Mode becomes a read-only facilities catalog over the same authored bunker
map. The inspector explains the selected installed room. Purchase prices,
placement previews, refunds, levels and power ranges are not displayed as real
state. Place/rotate remain disabled. Session shows the local operator, actual
profile generation and projected inventory, with no invented guests, code or
friend presence. It links to the same loadout/briefing/workspace routes.

UI commands are home-only at LocalGame; old epochs or requests during raid,
menu, deployment and settlement cannot open these screens. Existing feature
gates remain locked. This integration is useful navigation and real read-only
state, not completion of the post-MVP crafting/building/co-op mechanics.
